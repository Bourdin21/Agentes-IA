## 0. Salida mínima del agente

### 0.1 Alcance funcional resumido

API de facturación electrónica ARCA (ex-AFIP) que el ERP actual de Luciano Inmobiliaria consume para emitir comprobantes — honorarios, alquileres, entre otros — de forma individual o en lote. Multi-tenant: un mismo cliente (una inmobiliaria) puede operar con **más de un CUIT**, y cada CUIT puede tener **más de un punto de venta**. Se evalúa que cada inmobiliaria pueda gestionar su propio certificado de firma. Incluye control de suscripción/uso pensado para que Joaquín pueda detectar si un cliente está revendiendo el acceso más allá de lo contratado.

**Nota sobre el pedido "el cliente pregunta cómo ofrecemos nuestros servicios"** — no es un requerimiento funcional del sistema, es una pregunta comercial para responderle al prospecto. Respuesta directa según la política vigente del estudio (`27-presupuesto-parametros.instructions.md`, `31-formato-documento-cliente.instructions.md`): Olvidata Soft desarrolla software a medida con un flujo de trabajo en etapas (relevamiento → diseño → arquitectura → presupuesto aprobado → desarrollo → pruebas → entrega), cobrando **desarrollo a precio fijo** (50% al inicio / 50% a la entrega) más un **plan de mantenimiento anual** (hosting, soporte, actualizaciones de seguridad). **Para este proyecto puntual, ese modelo no encaja del todo**: al ser una API de uso variable (más o menos facturas, más o menos puntos de venta con el tiempo), lo natural es un modelo de **suscripción por uso/capacidad** en vez de (o adicional a) el mantenimiento fijo estándar — ver pregunta abierta §0.7-7. Vale la pena que Joaquín le responda al cliente con esa distinción: desarrollo inicial a precio fijo + suscripción recurrente ligada al uso real de la API, no el mantenimiento plano que se usa en el resto del portfolio.

### 0.2 Casos de uso principales

| # | Caso de uso | Actor | Resumen |
|---|---|---|---|
| CU-01 | Emitir comprobante individual | ERP del cliente (vía API) | Envía los datos de un comprobante (honorarios, alquiler, etc.) y recibe CAE/resultado de ARCA. |
| CU-02 | Emitir comprobantes en lote | ERP del cliente (vía API) | Envía un conjunto de comprobantes en una sola operación y recibe el resultado de cada uno. |
| CU-03 | Gestionar CUIT y puntos de venta | Inmobiliaria (panel propio) o Joaquín (gestión centralizada) | Alta de cada CUIT de la inmobiliaria y sus puntos de venta habilitados para facturar. |
| CU-04 | Gestionar certificado de firma | Inmobiliaria o Joaquín (según decisión, ver §0.7-1) | Carga/renovación del certificado `.p12` y clave privada asociados a cada CUIT. |
| CU-05 | Autenticarse ante la API | ERP del cliente | El ERP se identifica con una credencial propia (API key o similar) para poder facturar. |
| CU-06 | Controlar uso de la suscripción | Joaquín (panel interno, no visible al cliente) | Ver volumen de facturación por cliente/punto de venta y detectar patrones que sugieran reventa no autorizada. |
| CU-07 | Consultar estado de un comprobante | ERP del cliente (vía API) | Recupera CAE, número de comprobante y estado de un comprobante ya emitido. |

### 0.3 Criterios de aceptación verificables (selección crítica)

- **CU-01/CU-02**: un comprobante rechazado por ARCA devuelve el motivo de rechazo real (no un error genérico) para que el ERP del cliente pueda mostrarlo o reintentar. En lote, el fallo de un comprobante no aborta el resto del lote.
- **CU-03**: no se puede facturar contra un punto de venta que no esté dado de alta y habilitado para ese CUIT específico.
- **CU-04**: el certificado y su clave privada nunca se devuelven en ninguna respuesta de la API una vez cargados — solo se usan internamente para firmar contra ARCA.
- **CU-05**: una credencial de API inválida o de un punto de venta no habilitado no emite ningún comprobante (rechazo antes de tocar ARCA).
- **CU-06**: el panel de control de uso permite comparar el volumen real de facturación de un cliente contra los puntos de venta que declaró al contratar.

### 0.4 Permisos, estados y validaciones identificadas

**Actores**: (a) el ERP del cliente, autenticado como consumidor de API — sin UI propia, solo llamadas HTTP; (b) el cliente final (inmobiliaria), que **puede o no** tener un panel propio según se resuelva §0.7-1; (c) Joaquín, con acceso administrativo total (alta de clientes, CUITs, puntos de venta, planes, panel de control de uso) — rol reservado, no se documenta en el material comercial (mismo criterio que "SuperUsuario" en el resto del portfolio).

**Validaciones críticas**: CUIT válido (dígito verificador), punto de venta habilitado en ARCA para ese CUIT antes de intentar emitir, certificado vigente (no vencido) antes de firmar, límite de uso de la suscripción (bloqueo o solo alerta, ver §0.7-6).

### 0.5 Riesgos y supuestos

- **R1**: el motor AFIP/ARCA ya construido (`AfipService`/`AfipTokenCache`) asume **1 CUIT/1 certificado por instancia desplegada** (configuración en `appsettings`, no en base de datos). Extenderlo a multi-tenant (muchos CUIT/certificados en una sola API corriendo) es un cambio real de diseño — no una reconfiguración. El riesgo no es de viabilidad (es totalmente viable) sino de esfuerzo: hay que sacar el token WSAA y el certificado del mundo "un valor fijo en config" al mundo "un valor por fila en una tabla, cacheado por CUIT+PuntoVenta".
- **R2 (crítico, a comunicar directo a Joaquín antes de prometer algo al cliente)**: **no existe forma puramente técnica de impedir que un cliente revenda el acceso** a la API. Lo que sí se puede construir es *detección*: métricas de uso por punto de venta declarado, alertas cuando el volumen se dispara sin que el cliente haya dado de alta más puntos de venta, límites duros configurables (bloquear al superar X facturas/mes por punto de venta). La prevención real (impedir legalmente la reventa) es un asunto **contractual/legal**, no de software — se recomienda que la cláusula de no-reventa esté en el contrato de servicio, con el software dando la evidencia de uso para hacerla valer, no reemplazándola.
- **R3**: si cada inmobiliaria gestiona su propio certificado (self-service), el sistema pasa a custodiar credenciales sensibles de terceros (clave privada de firma digital) — exige cifrado en reposo fuerte (reutilizando el patrón de `century-21`) y define una superficie de responsabilidad legal/seguridad mayor a la de un proyecto típico del estudio.
- **R4**: "facturar en lote" en el motor AFIP actual no existe como concepto — hoy cada `Venta` dispara una llamada individual a WSFE en el momento de confirmar. Un modo lote implica orquestar N llamadas (posiblemente con reintentos parciales) y devolver un resultado consolidado — pieza nueva, sin precedente exacto. **Confirmado síncrono (§0.7-3)**: el lote completo debe resolverse dentro de una sola llamada HTTP — con WSFE respondiendo secuencialmente por comprobante, un lote grande puede acercarse a límites de timeout HTTP razonables; Arquitectura debe fijar un tamaño máximo de lote aceptado por request.
- **S1 (supuesto)**: el ERP del cliente es responsable de armar los datos del comprobante (montos, conceptos, receptor) correctamente — la API de Olvidata no valida reglas de negocio de facturación de honorarios/alquileres más allá de lo que exige ARCA, no reemplaza al ERP.

### 0.6 Banderas tempranas

- **Requiere migración EF**: Sí — proyecto nuevo (entidades: Cliente/Tenant, CUIT, PuntoVenta, Certificado, ApiKey, Plan/Suscripción, RegistroUso, Comprobante).
- **Integración externa**: Sí — ARCA/AFIP (WSAA/WSFEv1), reutilizando el motor ya construido, extendido a multi-tenant. **Nota**: `27-presupuesto-parametros.instructions.md` lista "Facturación electrónica AFIP/ARCA" como **exclusión fija estándar** del estudio — este proyecto es una excepción explícita a esa regla porque es literalmente el corazón del pedido, no un add-on. Marcar esto en el presupuesto para no aplicar la exclusión por inercia.
- **Máquina de estados**: Sí, acotada — estado del Comprobante (Pendiente → Emitido/Rechazado) y de la Suscripción (Activa → Suspendida por límite, si se define bloqueo duro).
- **Tipo de proyecto atípico para el estudio — resuelto 2026-08-14: es API pura, sin excepción.** El cliente confirmó explícitamente "el desarrollo va a ser exclusivamente de una Web API" (§0.10) — no hay panel MVC de ningún tipo, ni self-service ni backoffice. Los certificados entran por ingesta de una carpeta FTP compartida (proceso backend, no pantalla), y la gestión administrativa (alta de CUIT/puntoVenta, control de uso) se expone como endpoints que Joaquín consume directamente. Primer proyecto del estudio sin ninguna vista Razor/MVC.

### 0.7 Decisiones confirmadas (2026-08-13, Joaquín — gate de Análisis)

1. **Certificado — self-service confirmado (Opción B).** Cada inmobiliaria gestiona su propio certificado desde un panel propio. **Alcance ampliado explícitamente por el cliente**: hace falta construir la funcionalidad de autogestión (carga, renovación, validación de vigencia) **y además manuales de usuario** para que el personal de la inmobiliaria (no técnico) pueda hacerlo solo — esto es un entregable de documentación real, no solo código, y debe presupuestarse como ítem propio (ver `4-presupuestador.md`). Implica que el proyecto ya no es "API pura": necesita al menos una pantalla web de autogestión de certificados con su propia autenticación para el usuario final de la inmobiliaria.

2. **Multi-CUIT — una sola suscripción, cobrada por cantidad de CUITs (variante propia, no exactamente A ni B).** Una inmobiliaria contrata una única suscripción bajo la cual puede tener varios CUIT; el precio del pack escala según la cantidad de CUITs dados de alta. Confirma el modelo de datos: `Suscripcion` 1:N `Cuit` 1:N `PuntoVenta`, con el precio de la suscripción derivado de `COUNT(Cuit)`.

3. **Lote — ~~síncrono~~ revertido a ASÍNCRONO (2026-08-14, decisión final).** Tras confirmar síncrono el 2026-08-13, Joaquín pidió pasar **individual y lote** a asíncrono. Elimina el riesgo de timeout/tope de tamaño de lote (R6 queda sin efecto) a cambio de necesitar un mecanismo de consulta de estado — ver `2-disenador-funcional.md` §2.1 para el contrato revisado. **Pendiente de definir con el cliente**: ¿el estado se consulta por polling (`GET /comprobantes/{id}`) o el cliente prefiere que Olvidata le pegue a un webhook propio cuando el comprobante está listo? No asumido, ambos son viables técnicamente.

4. **Autenticación — API key simple por punto de venta (Opción A) confirmado.**

5. **Corte anti-reventa — bloqueo duro (Opción A) confirmado, con método propio para fijar el límite.** No se encontró benchmark público confiable de volumen de facturación de inmobiliarias argentinas (research realizado, sin resultado útil) — en vez de un número fijo inventado, el límite se ancla en lo que **el propio cliente declara** al contratar: Luciano informa un volumen esperado de facturas/mes por punto de venta, y el sistema bloquea al superarlo por un **multiplicador de seguridad configurable** (propuesto: 2x–3x, ajustable por Joaquín por cliente) — evita bloquear crecimiento legítimo, mientras que un salto de 5x-10x sin alta de nuevos puntos de venta es señal real de reventa. Mecanismo genérico, reutilizable para futuros clientes de la API, no hardcodeado a los números de Luciano.

6. **Modelo comercial — desarrollo a precio fijo + suscripción por packs de CUITs (recomendación aceptada, deriva de la decisión 2).** Reemplaza el mantenimiento anual plano estándar del estudio por una tabla de precios propia de este proyecto, escalonada por cantidad de CUITs activos — se define en `4-presupuestador.md`, no se fuerza dentro de la tabla STARTER/PRO/PREMIUM/SCALE existente (esa está pensada por cantidad de tablas de BD, no aplica a un producto de consumo de API).

**Respuesta a "cómo ofrecemos nuestros servicios" (para que Joaquín se la transmita al cliente)**: desarrollo a precio fijo (50% inicio / 50% entrega, como en todo proyecto del estudio) + suscripción recurrente en packs según cantidad de CUITs dados de alta (reemplaza el mantenimiento estándar en este caso puntual, por ser un producto de uso variable).

Joaquín consume esos endpoints administrativos directo (Postman/script), no hay ninguna vista Razor en este proyecto.

3. **Volumen real**: ~1.000 facturas/mes (reemplaza el "sin benchmark, ancla en lo declarado por el cliente" de §0.7-5 — ahora hay un número real de referencia, aunque sigue habiendo que declarar el volumen **por punto de venta**, no un total agregado, para que el control de uso siga siendo útil).

4. **Tipos de comprobante**: honorarios, **sueldos**, Facturas A/B/C. **Investigado 2026-08-14 (research específico pedido por Joaquín):**
   - **Honorarios/alquileres — confirmado, es una obligación real y ya resuelta conceptualmente**: desde la RG AFIP 4004-E, la facturación electrónica de alquileres es **obligatoria** para inmobiliarias que administran alquileres por cuenta y orden de terceros (del propietario). Mapea a `Concepto=2` (Servicios) vía Factura A/B/C, igual que ya está diseñado en `2-disenador-funcional.md` §2.1. **Detalle técnico nuevo a confirmar en Arquitectura**: cuando la inmobiliaria factura "por cuenta y orden" del propietario, el comprobante debe identificar al propietario (nombre/CUIT) como beneficiario — no es simplemente receptor=inquilino. No se tiene confirmado todavía el campo exacto de WSFEv1 para esto (puede requerir revisar el manual completo, no solo el código ya portado, que no cubre este caso) — ver R11 en Arquitectura.
   - **"Sueldos" — investigado, muy probablemente NO pertenece a esta API**: en el ecosistema ARCA/AFIP, "sueldos" remite al **Libro de Sueldos Digital / recibo de sueldo digital** — un sistema completamente distinto (para empleadores liquidando haberes a empleados en relación de dependencia), que **no usa WSFEv1** ni tiene relación con facturación electrónica de ventas/servicios. No hay forma de que "facturar un sueldo" tenga sentido dentro de este mismo motor de comprobantes. **Recomendación a Joaquín**: confirmar con el cliente si (a) "sueldos" era en realidad un uso coloquial de otra cosa (ej. honorarios de administración, que sí encaja), o (b) es un pedido genuinamente distinto (integración con Libro de Sueldos Digital) que, de confirmarse, es un **proyecto aparte**, no un tipo de comprobante más dentro de esta API — no se incluye en el presupuesto actual bajo ningún concepto hasta que se aclare.

5. **Individual + lote**: confirma lo ya definido (§0.7-3, síncrono).

6. **~100 CUIT con múltiples puntos de venta** — es un salto de escala enorme respecto de lo asumido al presupuestar (los packs de `4-presupuestador.md` llegaban hasta "16+ CUITs, a cotizar caso por caso"). **A 100 CUIT, el proyecto entero cambia de categoría comercial**: dimensionamiento de infraestructura (100 certificados vigentes simultáneos, 100 tokens WSAA cacheados), volumen real (~1.000 facturas/mes repartidas entre 100 CUIT es un promedio bajo por CUIT, pero la distribución real puede ser muy despareja), y sobre todo **precio** — no se puede cotizar con la tabla de packs pensada para una inmobiliaria chica. Se marca explícitamente como punto a resolver con Joaquín antes de cerrar `4-presupuestador.md` (ver esa memoria).

**Reencuadre del control de uso / anti-reventa (importante)**: con ~100 CUIT propios bajo un solo cliente que además tiene su propio SaaS, el escenario ya no es "una inmobiliaria chica revendiendo el acceso a otras" — Luciano **ya es** una plataforma que sirve a (probablemente) ~100 inmobiliarias/unidades de negocio distintas, de forma legítima. El control de uso sigue teniendo valor (asegurar que la facturación agregada sea consistente con lo contratado), pero el R2 documentado en `4-presupuestador.md`/versión anterior de este archivo pierde parte de su sentido original — no se trata de "detectar reventa no autorizada de un solo cliente pequeño" sino de "facturación precisa de un cliente grande multi-tenant". No se descarta el mecanismo, se reencuadra su propósito.

### 0.11 Nueva rama: extracción de datos de contrato desde PDF con IA (pedido nuevo, 2026-08-14)

El cliente preguntó si es viable agregar, **como rama separada** de la API, una funcionalidad que reciba un PDF de contrato cargado por el usuario (en el frontend propio del cliente, no en algo que construya Olvidata), lo procese con una herramienta de IA, y devuelva los datos extraídos para autocompletar un formulario que el cliente ya tiene en su propia UI.

**Viabilidad — sí, es viable y con una vía técnica concreta**: los modelos Claude de Anthropic (la misma familia de IA con la que se construye este estudio) soportan **entender PDFs de forma nativa** — se le pasa el documento directamente en la consulta y devuelve una extracción estructurada (JSON) sin necesidad de armar un pipeline de OCR aparte. La API de Olvidata expondría un endpoint nuevo, ej. `POST /api/v1/contratos/extraer`, que recibe el PDF, lo manda a la API de Claude con una consulta que pide específicamente los campos del contrato inmobiliario (partes, dirección del inmueble, monto, fechas, duración, etc.) en un formato JSON fijo, y devuelve ese JSON — el frontend del cliente lo usa para autocompletar su formulario, no lo hace el sistema de Olvidata.

**Es una rama funcionalmente independiente** del motor de facturación — no comparte modelo de datos ni máquina de estados con Comprobante/CUIT/Certificado. Se trata como módulo propio en Diseño/Arquitectura/Presupuesto, no como extensión de lo ya construido.

**Riesgos a documentar (no asumir silenciosamente)**:
- Precisión de extracción: un modelo de IA puede equivocarse o no encontrar un dato — el diseño debe asumir que el usuario **revisa y corrige** el formulario autocompletado antes de guardar, nunca que el llenado es 100% automático sin supervisión humana.
- Costo variable: cada llamada a la API de Claude tiene un costo por uso (tokens) — a diferencia del resto del sistema (costo fijo de desarrollo + suscripción), esta rama tiene un costo operativo variable por PDF procesado, que hay que trasladar al modelo comercial de alguna forma (¿incluido en el pack, o cobrado aparte por volumen de PDFs procesados?) — pregunta abierta para el Presupuesto.
- Datos sensibles: los contratos inmobiliarios tienen datos personales (DNI, domicilios) — confirmar que el envío a un proveedor de IA externo (Anthropic) es aceptable para el cliente en términos de privacidad/cumplimiento, mismo criterio de transparencia que se aplicó al certificado de firma digital.

### 0.12 Research de mercado para ajustar precios (2026-08-14, pedido explícito de Joaquín)

Se investigaron competidores reales que ofrecen exactamente el mismo tipo de producto (API de conectividad a WSFEv1/ARCA, cobrada por cantidad de CUIT) — el más comparable es **AfipSDK** ("la plataforma preferida entre desarrolladores para conectarse a los web services de AFIP/ARCA", +100k descargas). Su tabla de precios real (2026-08-14):

| Plan AfipSDK | CUIT incluidos | Requests/mes | USD/mes |
|---|---:|---:|---:|
| Free | 1 | 1.000 | 0 |
| Pro | 10 | 10.000 | 25 |
| Growth | 100 | 100.000 | 80 |
| Startup | 1.000 | 1.000.000 | 250 |

**Implicancia directa**: el paquete "Enterprise" propuesto en la primera versión de `4-presupuestador.md` (~USD 2.700/año para ~100 CUIT) es **~2,8 veces más caro** que el plan Growth de AfipSDK para la misma cantidad de CUIT (100 CUIT = USD 80/mes = USD 960/año). Esto no es directamente comparable 1:1 — AfipSDK es solo conectividad cruda a WSFEv1 (el cliente arma toda su propia capa de negocio encima), mientras que Olvidata ofrece gestión completa de certificados (ingesta FTP en vez de subida manual por CUIT), control de uso/anti-reventa con señales, y lógica de negocio ya adaptada a inmobiliarias — pero **dado que Luciano confirmó tener capacidad técnica real** (tiene su propio SaaS), es una alternativa competitiva real que evaluarían: contratar AfipSDK directo y construir la capa multi-tenant ellos mismos. **Se recalculó la tabla de precios en `4-presupuestador.md` anclada en estos valores reales, con una prima moderada (no un múltiplo arbitrario) justificada por el valor agregado real, no por "somos mejores".**

**Research adicional (2026-08-14, segunda ronda — evaluando si conviene bajar otro 20%)**: Joaquín preguntó si el precio seguía caro tras la corrección de mercado. Dos hallazgos nuevos: (1) Xubio (SaaS de facturación argentino grande) cobra USD 26-156/mes según plan — no es comparable directo (es B2C, no una API mayorista), solo da contexto de rango general. (2) **Hallazgo relevante**: FacturaGratis tiene un plan específico "Multi-CUIT para administradores" — exactamente el caso de Luciano (facturar en nombre de terceros, no multi-tenant genérico) — y **ese plan no tiene precio público**, el sitio remite a "consultar dentro del proceso de vinculación de cuenta". El competidor más parecido al caso real trata esa configuración específica como venta consultiva, no como tier de catálogo — consistente con que "facturar por cuenta y orden de terceros" (R11) es más complejo de compliance/soporte que un multi-tenant genérico. **Conclusión (consultada con `/olvidata-ceo`): no bajar el precio — este segundo research refuerza la prima del 44% sobre AfipSDK en vez de debilitarla.** Recomendación de `/olvidata-ceo`: si hay objeción real de precio del cliente, la palanca es un escalón de entrada más chico o descuento por compromiso multianual, no bajar el precio de lista — más aún tratándose de un caso ancla para una categoría de producto nueva del estudio.
