Every document delivered to a client (budget proposals, the documentador's sprint summary) must follow the **OlvidataSoft document format** defined in `.github/instructions/31-formato-documento-cliente.instructions.md`: brand header (wordmark + divider + title + "OlvidataSoft · Month Year"), then sections in order — `## Sobre el sistema` (narrative bullet walkthrough, 2nd person/voseo) → optional `## Como funciona X — paso a paso` for non-trivial flows → `## Rol de usuario` table → pricing section → `## Que incluye` / `## Que no esta incluido` → `## Lo que necesitamos de tu parte` → `## Condiciones comerciales` → a mandatory closing signature line (`**Olvidata Soft — email — website**`).

**Why:** User (2026-07-03) provided a real OlvidataSoft commercial proposal (CRM + WhatsApp Chatbot + Buscador de Propiedades, a SaaS-tier product) as the reference style and asked that all future client documents use this format. When asked whether this replaces the existing pricing content rules (Etapa 1/Etapa 2, PERT table, Tokens IA 10% line item) or just the visual/structural style, user confirmed: **only style/structure changes** — the underlying pricing content rules in `27-presupuesto-parametros.instructions.md` stay as-is for custom hourly-billed dev projects. The "Planes disponibles" (annual SaaS tiers) section from the example is specific to productized/SaaS offers; custom dev projects keep Etapa 1/Etapa 2/Tokens IA/Mantenimiento tables, just wrapped in the new header/footer/section-order/tone.

**How to apply:** Encoded in the repo so agents pick it up automatically — `31-formato-documento-cliente.instructions.md` is now referenced from `presupuesto-mvc.agent.md`, `04-presupuesto.prompt.md`, `documentador.agent.md`, `07-documentacion.prompt.md`, and listed in `CLAUDE.md` / `.github/copilot-instructions.md`. The template `docs/templates/proyecto/presupuesto-cliente.md` was rewritten to match. Internal agent memory files (`docs/<proyecto>/definiciones/*.md`) are explicitly NOT subject to this format — they keep their technical internal structure. Related: [[project-agentes-ia]], [[feedback-tokens-ia-10-porciento]].

**Addendum (2026-07-03, superseded same day — see correction below):** ~~publish every client document via the Artifact tool with a custom-designed visual treatment (palette/typography chosen fresh per subject).~~ **The user rejected this within the same session**: "no me sirvió porque me cambia el formato, las letras, y todo el documento, volver a la version anterior." A custom Artifact re-styling is exactly the wrong move for these documents — it fights the whole point of a standardized studio format.

**Correction (2026-07-03, same day):** client-facing documents (budgets, sprint summaries) must **never** get bespoke visual design (no custom palette, no custom font pairing, no `artifact-design` skill) — they must look like plain, consistent business documents: default headings, bold, bullet/numbered lists, tables, no color scheme. This matches the real Drive precedents (e.g. `Presupuesto Ulises - OlvidataSoft.docx`, `CRM, Chatbot WhatsApp y Buscador de Propiedades.docx`), which are unstyled Word docs with the section structure from `31-formato-documento-cliente.instructions.md` and nothing else.

**How to deliver (established this session):** the user's actual deliverable format is a **Word file in their Google Drive**, not a web Artifact. The user's Drive already holds every past proposal/sprint-summary as a `.docx` in the shared folder `parentId: 0AKdL2qlDPnZIUk9PVA` (owner `olvidatasoft@gmail.com`). To produce a new one:
1. Write the content as clean **semantic HTML** (real `<h1>`/`<h2>`, real `<ol>`/`<ul>`, `<strong>`/`<em>` — no `<style>`, no CSS, no custom fonts/colors).
2. Upload with `mcp__claude_ai_Google_Drive__create_file`, `contentMimeType: "text/html"`, `parentId: "0AKdL2qlDPnZIUk9PVA"`, default conversion (do NOT set `disableConversionToGoogleType`) — this lands as a native Google Doc (`application/vnd.google-apps.document`) that the user can open and download as Word themselves.
3. **Do not hand-write Markdown for this step** — a real .md → Google Doc conversion (via copy-paste or an external pipeline) is what mangled heading levels and silently dropped the ordered-list numbering the first time (verified by reading the resulting broken `.docx` back with `read_file_content`). Semantic HTML converts far more reliably than Markdown text.
4. After creating, read the file back with `read_file_content` to confirm headings/lists survived before telling the user it's ready.
5. The `.md` file in `docs/<proyecto>/` stays the internal versioned source of truth for content; the Google Doc in Drive is the client-facing deliverable. Don't delete a pre-existing (possibly broken) file in Drive without asking — just create the corrected one alongside it and flag the old one.
